Section 05.6
🧠What I Need to Configure Rev.io — Knowledge Requirements

The API surface is accessible. The transcript intelligence is flowing. The missing link is institutional knowledge — the same tribal knowledge an experienced SA holds in their head after 50+ onboardings. This section maps exactly what documentation, context, and reference material I need to move from briefing the SA to doing the work before they ever open the account.

Items are tiered by impact: Tier 1 gates automation entirely · Tier 2 prevents the most common rework · Tier 3 enables best-in-class outcomes.

Tier 1 — Gates Automation Can't reliably pre-configure without these
1. PSA Configuration Schema Reference
Equivalent of a psa-reference.md — field names, valid values, object dependencies
I need to know: All configurable elements of a PSA instance — ticket types and their standard taxonomy (Install? Break/Fix? Project? Maintenance? Preventive?), service board structure, user role definitions and permission matrix (Technician / Dispatcher / Manager / Admin / Billing Admin?), SLA config options, dispatch board settings, and the order-of-operations for setup (what must exist before what).
Rework prevented without this:
Wrong ticket types created → SA rebuilds in session 1. Wrong user roles → permission errors on day 1. Wrong setup order → cascade failures in config.
Owner: Product / SA team — internal PSA config docs or Notion SA runbook
2. Integration Setup Guides (QB, NinjaOne, PAX8, HubSpot)
Step-by-step config for each integration, including required field mappings
I need to know per integration: Required auth credentials and where they live, which fields sync bidirectionally vs. one-way, GL account mapping logic (QB Online: which Rev.io product types map to which QB chart-of-accounts codes?), what triggers a sync, known gotchas (e.g. QB Desktop = not supported today — what's the workaround path I set up instead?), and which integrations can be configured pre-kickoff vs. require client credentials at the call.
Rework prevented without this:
Integration configured wrong → SA manually re-maps GL codes in session 2. QB Desktop client gets wrong setup path. NinjaOne asset sync breaks because field mapping was guessed.
Owner: SA team + product integration docs — likely exists internally for ConnectWise, QB Online at minimum
3. Data Migration CSV Templates + Field Mapping Guide
Exact formats the data engineering team ingests; field-level mapping from source systems
I need to know: CSV column structure for customers, contacts, products, assets, historical tickets. Which fields are required vs. optional per object type. Field-level mapping from ConnectWise, Halo, HouseCall Pro, TigerPaw, and Zoho to Rev.io equivalents. What data can NOT be migrated and requires manual re-entry. Max lookback window for each data type (currently: 2 years tickets, 6–8 months media).
Rework prevented without this:
Wrong CSV format → data engineering rejects file → migration delayed. Missing field mapping → manual re-keying of 100s of customers. Client told wrong data scope → expectation failure.
Owner: Data engineering team — they have these templates; SA team should have field mapping guides
4. Required API Credentials & Auth Flows Per Integration
What client-side credentials I need to collect before I can wire up integrations via API
I need to know: For each integration — exactly what the client needs to provide (QB Online: OAuth2 flow? or client ID/secret?), what can be pre-staged vs. what requires live client presence, and whether there's a dev/sandbox mode for each integration so I can pre-wire the connection before client credentials are available.
Rework prevented without this:
Integration can't be set up pre-kickoff because I collected the wrong credentials type. SA loses 20 minutes of kickoff call on credential collection that should have been async.
Owner: SA team — likely covered in kickoff prep checklist if it exists
Tier 2 — Prevents Most Common Rework Skipping these = second session wasted on corrections
5. Client-Type Configuration Templates
Standard starting configs by vertical: MSP · Security Integrator · AV · Multi-service
From the 103 recordings across 12 wins, four distinct profiles emerge. Each needs a different baseline. A standard MSP (RavGuard, ShinnTek) needs RMM integration, recurring managed service tickets, and a simple dispatch board. A security integrator (Remote Technology, Castle Security) needs install project tickets, inventory tracking, dispatch by technician. A mixed-services shop (First Class Technology, GuentherTech) needs both tracks plus product-heavy quoting. I need a template per vertical that defines the default service boards, ticket type sets, user role matrix, and billing cycle structure so I'm not making it up from scratch each time.
Owner: SA team + Brooke Lee (MSP community / best practices)
6. Prior PSA Migration Runbooks
Source-specific gotchas: ConnectWise, Halo, HouseCall Pro, Zoho, Autotask
Each source system has unique field structures and migration traps. ConnectWise: tickets have boards and sub-types that don't map 1:1. Halo: custom field schemas that have no Rev.io equivalent. HouseCall Pro: it's a field service tool, not a PSA — migration is mostly manual. Zoho: depends entirely on how they configured it. I need per-source runbooks that document what transfers cleanly, what needs transformation, what should be left behind, and what the client needs to manually re-create.
Owner: Data engineering team — they've run thousands of these migrations
7. Top 10 Rework Patterns from SA Team
What SAs fix in session 2 because it was set wrong in session 1
This is the highest-leverage input for automation. I don't need all 50 pages of the SA playbook — I need the 10 things that cause the most correction work. Examples I'm guessing at: GL codes mapped to wrong accounts → corrected at first invoice run. Billing cycle set to monthly when client bills quarterly. Wrong tax jurisdiction on customer record. Ticket statuses missing a "pending client" state clients always want. Service boards created too narrowly (separate board per tech instead of one dispatch board). 30 minutes with a senior SA would give me this list.
Owner: SA leads — Nicole Hills, Kegan Ehlers, Halle Taylor, Tony Mehner
8. Kickoff Session Agenda + What Gets Configured Live
What the SA does with the client present vs. what can be pre-built
I need to know which configurations are done with the client on screen (because they're demonstrating value or gathering live input) vs. which should just be done. If I pre-configure something the SA uses as a teaching moment, I've stolen a session activity without realizing it. I need the session-by-session agenda so I can identify exactly where pre-automation inserts cleanly. The goal: SA shows up with 70% done, uses session time for the 30% that actually requires the client's judgment.
Owner: SA manager — onboarding methodology docs / 13-milestone checklist
Tier 3 — Best-in-Class Outcomes Client goes live faster, never needs to undo anything
9. GL Code Standard Mappings by Accounting Software
QuickBooks Online chart-of-accounts → Rev.io GL code structure
When I know the client uses QB Online, I can pre-map their GL codes to the standard QB chart-of-accounts structure before the kickoff. Right now SAs map this manually in every engagement. A reference table (QB account type → Rev.io GL code category → typical account numbers for MSPs) would let me auto-populate 80% of GL codes before anyone touches the keyboard.
Owner: Finance / accounting team — standard MSP chart-of-accounts is well-known
10. Product Catalog Naming Conventions + Category Structure
Standard taxonomy so catalog doesn't become a mess 6 months in
Bullfrog Group's transcript showed exactly what happens without this: a product catalog that grew organically over years with inconsistent names, wrong GL codes, and duplicate entries that don't match. If I pre-build the catalog structure using Rev.io's recommended naming conventions and category/subcategory hierarchy, the client starts clean and doesn't develop the same technical debt.
Owner: SA team — best practices guide or example clean catalog
11. Invoice Template Library + Billing Cycle Playbook
Standard templates by client type; billing cycle guidance by revenue model
From transcripts: some clients bill monthly, some quarterly, some milestone-based (installation phases). Each needs a different invoice template structure. A library of Rev.io invoice templates mapped to client types — MSP monthly, project-based milestone, mixed recurring + T&M — would let me pre-configure the right one based on what the transcript reveals about how they bill today.
Owner: SA team + billing platform team
12. Feature Availability Matrix (Live vs. Roadmap)
What's available now vs. Apollo 2/3 — so I don't pre-configure around a feature that doesn't exist yet
Several clients in the scorecard were told features are "coming in April" (sales pipeline, QuickBooks Desktop integration). If I pre-configure expecting a feature that isn't live yet, the SA walks into a broken environment. I need the current feature availability state — specifically: which integrations are GA, which are beta, which are roadmap-only — so I configure only what's actually deployable today.
Owner: Product team — roadmap Notion page (read-only access already available)

Section 05.7
🎯CEO Design Parameters — What the Automation Must Be Built Around

From Brent Maropis to Fran Timothy, March 18 2026 — forwarded as design constraints for the Kaia onboarding automation pipeline. These are not aspirational. They are the operating parameters the system must be built to enforce.

Parameter 1 — Kickoff Timeline
Same day or next day. Always.
  • Closes before lunch → kickoff scheduled that afternoon
  • Closes after lunch → kickoff scheduled next morning
  • Exceptions: rare, documented, shared accountability Sales + Onboarding
  • Capacity scoring eliminated. Replace with batter's box rotation — next SA in line takes the next deal, no deliberation
Automation implication: Pre-config must complete before kickoff. If deal closes at 11am, the environment needs to be partially built by 2pm.
Parameter 2 — Status Definitions
Every status needs a timeline and an owner.
  • On Track — client engaged, milestones on schedule, SA owns, reviewed weekly
  • Off Track — behind on a milestone, SA escalates to Fran within 24 hours
  • On Hold — hold date mandatory at time of status set; no hold date = immediate RTS
  • RTS — Sales engages within 24hrs; no path back in 5 business days = formally canceled
  • Cancel — specific subcategory required, no undocumented cancellations
Parameter 3 — Cancellation Reasons
"Other" and "Fail to Launch" are eliminated.
  • Functionality — must specify exact product or feature gap
  • Client Initiated / Business Change — specific reason required (OOB, acquisition, budget cuts)
  • Ambiguous cancellations escalate to Fran before logging
If a client cancels, it inherently failed to launch. We need to understand why — that data feeds back into improving the process.
Parameter 4 — Go-Live Duration Targets
Complexity drives timeline. Simple clients don't wait.
  • ≤$700/mo, no data or payment migration → live within 1 week
  • With payment migration → live within 3 weeks
  • Billing clients → defined, documented, tracked timeline
  • These targets shrink materially over the next 12 months as automation matures
Automation implication: The 1-week target is only achievable if pre-config eliminates Day 1 setup time entirely for simple clients.
Parameter 5 — Automated Cadence for On Hold / RTS
System driven. Not manual.
  • Day 0 — SA phone call
  • Day 2 — No response → SA follow-up email
  • Day 4 — No response → escalate to Fran + automated email from Brent flagging cancellation risk; Sales copied
  • Day 6 — No response → Sales notified, account moves to RTS if still on hold
  • Day 10 in RTS — No re-engagement → formally cancel + log reason
Sales and Onboarding share accountability. This is not owned by one team.
Parameter 6 — Cancellation Rate Targets
Current: ~25% → Target: 15% → Long-term: 10%

Every workflow decision, cadence timing, escalation trigger, and RTS threshold must be built to close this gap. On Hold and RTS pools must be actively managed — the overwhelming majority of clients must remain On Track.
Parameter 7 — Client Obsession and Platform First Execution
Revii first. AI first. Every instance, every time.
None of these parameters compromise focus on extraordinary service — they are designed to support it. This requires intentional training, clear measurements, strict adherence, and real accountability to setting up the platform Revii first / AI first, in a way that enables telemetry, ease of integration, and long-term scalability.
What "Platform First" means for automation
  • Revii AI configured and enabled in every new instance before kickoff
  • Integrations wired to enable telemetry from day 1 (not retrofitted)
  • Configuration follows a schema that enables long-term scalability — no shortcuts that create technical debt at go-live
  • Done correctly, this discipline delivers the best possible client experience
⚡ What These Parameters Demand from the Automation Pipeline
Speed requirements
  • Pre-config must run in minutes, not hours — same-day kickoff is non-negotiable
  • Simple clients (≤$700/mo, no migration) need a nearly complete environment by kickoff
  • Batter's box rotation removes the deliberation buffer — there's no time to manually prep
Quality requirements
  • Revii must be configured and enabled — not optional, not post-launch
  • Integration telemetry must be wired from Day 1, not retrofitted
  • Configuration schema must support long-term scalability (no shortcuts)
Accountability requirements
  • Every automated action must be logged with a reason — mirrors the cancellation reason mandate
  • Automated cadence (Hold/RTS) must be system-enforced, not dependent on SA discipline
  • Cancellation data feeds back into automation improvement — closed loop

Section 07
❓The 7-Question Handoff

These questions fill the gaps that transcripts don't reliably surface. Ask during the sales process AND as a structured 5-minute segment at the end of the closing call.

1
"What PSA/ticketing system are you currently on?"
→ Unlocks: Data Import template, migration approach, legacy data handling
2
"What accounting software do you use? QuickBooks Online, Desktop, NetSuite, or other?"
→ Unlocks: Integrations milestone — specific QB connector type
3
"What RMM are you running? NinjaOne, Datto, ConnectWise Automate, or other?"
→ Unlocks: Integrations milestone — RMM connector selection
4
"How many people need access to Rev.io? Any specific roles — field techs, dispatchers, billing admin?"
→ Unlocks: Admin milestone — user account creation with correct roles
5
"Do you dispatch by department, geography, or skill set? Or some combination?"
→ Unlocks: Processes milestone — dispatch board configuration approach
6
"What's your current invoice number sequence? Do you need continuity with your legacy system?"
→ Unlocks: Company Info milestone — invoice numbering config
7
"What payment processor do you use today? Same processor or switching?"
→ Unlocks: Payments Configuration milestone
The explicit close: "Before we wrap up — we're going to set up your Rev.io environment before your first onboarding call so your team hits the ground running. Can I take 5 minutes to confirm a few details? [Run through the 3–4 most relevant questions based on the call.]"

⚖️Before vs. After
😤 Today — Blank Instance
📭 Client logs in to an empty Rev.io instance
🔄 Session 1: "What's your company name? Who are your contacts? What system are you from?"
😩 Client: "I thought we covered this in sales…"
⏱️ Sessions 1–2 wasted on re-collecting setup information
😤 SA frustration — client frustration — slow start
📉 Later start on actual training → longer time-to-value → higher churn risk
🚀 With Pre-Config — Day 1 Ready
✅ Client logs in — their company, team, and settings already there
💬 SA opens: "We set this up based on your sales conversations. Here's what's done. Here's what we still need from you."
🎓 Session 1 goes straight to training — not setup
🤝 Client feels known and cared for from the first minute
📈 Faster graduation → better NPS → lower churn
